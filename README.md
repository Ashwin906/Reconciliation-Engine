# Reconciliation Engine

**A merchant cannot prove the money that landed in their bank is the money they were owed. This reconstructs that proof automatically, shows the arithmetic, and tells the truth about the parts it can't explain.**

Built for Razorpay Buildathon, Track 04 — AI Finance Controller.

If you read nothing else: **[FAILURES.md](FAILURES.md)** — every real bug found while building this, how it was caught, and what it changed. **[EVALUATION.md](EVALUATION.md)** — what the metrics actually mean and don't mean.

---

## What this is

Every rupee a merchant collects through Razorpay has to end up somewhere: paid out, refunded, taken by a chargeback, kept as a fee, or held in reserve. This system:

1. **Matches** settlements against bank credits — exact lookup first, then a deterministic set-match, then fuzzy matching for identity-only noise (a changed reference number, a truncated bank narration). Never fuzzy-matches on *amount* — money either ties or it's a real gap, never "approximately correct."
2. **Verifies independently** — every match's arithmetic is re-derived from raw data by code that shares nothing with the matcher that produced it (`DECISIONS.md` D-02), and rejects the matcher's own claims when they don't hold up.
3. **Proves conservation** — sums every rupee collected against every door it could have left through, closing to exactly ₹0.00 as a proof of completeness, not a statistic.
4. **Detects leaks** a human would never spot — a fee rate drifting 0.36% off contract across 1,200 transactions looks like nothing per-row and like real money in aggregate.
5. **Investigates the unexplained residue with an LLM** — but the model only *proposes*; every hypothesis is independently re-verified before it can be trusted, and a gate — deterministic, no LLM, exhaustively tested — decides whether a verified correction auto-applies, needs a human, or gets rejected outright.
6. **Records every decision permanently** — an append-only ledger; a correction is a new row, never an edit to an old one.
7. **Shows the whole journey happening** — "Watch it happen" replays a real merchant problem end to end (customer pays → Razorpay captures → settlement batched → bank credits → matching tiers → investigation → gate → conservation proof), with the money traced stage by stage. Every scenario is driven by a real defect injector from `gen/defects.py`, and every number shown is read out of a genuine `run_batch()` — `sim/journey.py` narrates the pipeline, it does not reimplement it.
8. **Lets you break it yourself** — choose which defects to inject and how severe, then watch the same pipeline handle inputs nobody prepared for. The controls are generated by introspecting the injectors' real signatures (`sim/catalog.py`, `DECISIONS.md` D-27), so what is on screen is exactly what the code accepts — it cannot drift into offering a knob that does nothing.
9. **Shows where the money went** — a Sankey built directly from the conservation identity (`DECISIONS.md` D-29): collected splits into what reached the bank, each named deduction, and anything unaccounted for. The picture and the proof are the same numbers, so they cannot disagree.
10. **Lets you make the AI lie, and watch it fail** — swap the investigator for one deliberately trying to get a false correction onto the books (fabricated evidence, a real amount understated to sneak under the auto-approve limit, real-but-wrong evidence, unearned confidence). Each attack targets a different defence, and nothing downstream of the model knows the mode exists (`sim/adversary.py`, `DECISIONS.md` D-30). The headline case: the model cites a real dispute and claims the adjustment is **₹0.01** when it is actually **₹2,463.28** — the gate recomputes it from raw data, sees it exceed the ceiling, and routes it to a human instead of applying it. That exact bug shipped once (`FAILURES.md` #1); this is the regression test you can watch.
11. **Tracks the rolling reserve across months** — money withheld in one period and returned in another is the *same* money, and a single-period tool reports a false alarm in both directions: an unexplained shortfall when it is held, an unexplained credit when it comes back. `reserve/ledger.py` models holds with real release dates, which closes a gap three separate modules had independently documented as blocking them (`DECISIONS.md` D-31). The demonstration is narrow and checkable: every period **fails** conservation without the ledger and **closes to ₹0.00** with it, over identical data.
12. **Proves the architecture earns its complexity** — every run is also scored by a deliberately naive exact-match reconciler (`sim/naive.py`, `DECISIONS.md` D-28) and shown side by side. On a rewritten reference number the naive version reports money missing that actually arrived; on a fee overcharge it reconciles at 100% and misses the loss entirely. A test asserts the real pipeline never scores worse — if it ever did, that would be reported, not removed.

13. **Runs on a real Razorpay account, not only simulations** — `ingest/assemble.py` converts live API payloads into the same `Dataset` every other module reads, so the entire pipeline works unchanged on real data (`DECISIONS.md` D-34). Credentials live in the server environment and never touch the browser (D-33), and every Razorpay call is a read. The one class that actually performs the HTTP call has never run against a live endpoint — stated in the product's own `/live/status` response rather than buried here.

**The app ships with no data.** There is no seeded merchant and no placeholder dataset: every figure on every screen originates from a simulation the viewer explicitly ran and watched execute. The journey view and the dashboard are two renderings of one run, so they cannot disagree.

The full domain background is in **[DOMAIN_KNOWLEDGE.md](DOMAIN_KNOWLEDGE.md)**. Every non-obvious design choice, with what was rejected and why, is in **[DECISIONS.md](DECISIONS.md)**. A function-by-function account of what was built, how, and what broke along the way is in **[FUNCTION_REFERENCE.md](FUNCTION_REFERENCE.md)**.

## Quick start

### Docker (recommended)

```bash
docker compose up
```

Backend: `http://localhost:8000` (interactive API docs at `/docs`). Dashboard: `http://localhost:5173`.

> **[UNVERIFIED end-to-end]** — Docker Desktop was not running on the machine this was built on (checked repeatedly). Every image builds from standard, unremarkable Dockerfiles and the application itself is proven by 476 passing tests; what's specifically unverified is the containerized run. If `docker compose up` doesn't work cleanly, that's the first thing to fix, and `Dockerfile`/`web/Dockerfile`/`docker-compose.yml` are short enough to debug quickly.

### Without Docker

```bash
pip install .
uvicorn api.main:app --reload         # backend, :8000

cd web && npm install && npm run dev  # frontend, :5173, separate terminal
```

`landing.html` is a standalone product page that opens in any browser with no build step.

The app starts **empty** — no seeded merchant, no sample data. Open the dashboard, go to **Watch it happen**, and run a scenario; that run becomes the live data on every other screen. "Clear all" resets to empty.

This is deliberate (`DECISIONS.md` D-24): a seeded dataset sitting alongside the simulator would show numbers that merely *resembled* it, with no way to tell which screen reflected which run.

### Using a real Razorpay account (optional)

```bash
RAZORPAY_KEY_ID=rzp_test_xxxx
RAZORPAY_KEY_SECRET=xxxx
```

Set those in the server's environment and restart, then use **Watch it happen → Use your real Razorpay account** to reconcile a real date range. The dashboard has no field for an API secret on purpose (`DECISIONS.md` D-33): keys live in the server environment and never travel through the browser or any request body.

Every Razorpay call is a **GET** — this system cannot write to a merchant's account. Start with **test-mode** keys.

> **[UNVERIFIED]** `ingest.razorpay.RequestsTransport` — the one class that actually talks to Razorpay — has never run against a live endpoint, because no real keys existed while this was built. Everything either side of it is tested against recorded payloads, and `GET /live/status` reports this honestly rather than implying a verified integration.

Bank data comes from a CSV path on the server (`ingest/bank/generic_csv.py`). Without one, settlements have nothing to match against, and the run says so explicitly instead of reporting 0% matched.

### Enabling AI investigation (optional)

```bash
cp .env.example .env   # fill in GROQ_API_KEY
```

Without a key, the system runs completely normally — every unresolved case honestly stays unresolved instead of being investigated (`DECISIONS.md` D-08). This is the actually-tested path throughout this build; adding a key is additive, not a mode switch to something more "real."

## Running the tests

```bash
python -m pytest tests/ verify/ -q
```

476 tests, all passing, ~3 seconds. `verify/` is included deliberately — it holds the build-breaking guard that proves the independent verifier never imports the matcher's logic (`DECISIONS.md` D-02).

```bash
python -m evalh.cli --seed 42 --out eval_results
```

Produces `metrics.md` and `exceptions.md` from one command — the honest numbers `EVALUATION.md` walks through.

## Architecture

```
core/        money (integer paise, never float), IST calendar, the Proof contract
gen/         synthetic data generator + 13 defect injectors, with planted ground truth
ingest/      Razorpay client, bank CSV adapters, idempotent upserts,
             and assemble.py -- real API payloads -> the pipeline's own Dataset
match/       T0 exact-id -> T1 UTR -> T2 internal-consistency -> T3 fuzzy
verify/      independent re-derivation -- shares no code with match/, enforced by a build guard
invariant/   the conservation identity + per-settlement localisation
detect/      11 leak-detection rules + 2 cross-batch pattern scans
agent/       Groq-backed T4 investigation of unresolved residue
gate/        AUTO / HUMAN / REJECT -- pure function, no I/O, no LLM
ledger/      append-only decision record
reserve/     rolling-reserve holds with real release dates -- pure, no I/O
sim/         scenario catalogue, journey narration, defect introspection, naive
             baseline, adversarial transport, multi-period reserve demo
             -- reads real pipeline output, computes no reconciliation of its own
evalh/       the eval harness -- first honest numbers, Phase 6
pipeline/    the real orchestrator wiring every phase above into one loop
api/         FastAPI routes + webhook signature verification
web/         React + shadcn/ui dashboard -- Watch it happen, Overview, Needs attention,
             Activity log, Reports
landing.html standalone product page, built from the dashboard's own design tokens
```

Built in 18 phases, in order, each with its own tests before the next began (14 planned, plus `sim/`, `reserve/`, the real-account path and an interface rebuild — see `BUILD_PLAN.md`). The full build log — what each phase built, what broke, how it was fixed — is `FUNCTION_REFERENCE.md`.

## What's deliberately out of scope

INR only. Razorpay only. CSV bank ingest (an Account Aggregator adapter is a config change, not a rewrite — `ingest/bank/base.py`'s interface is built for it). Bank-statement **upload** is not wired — a real run takes a CSV path already on the server. No accounting-software integration — CSV export instead. No mobile app. Each is a stated decision (`DECISIONS.md` D-22), not an oversight — one loop closed properly beats four loops at 70%.

## Where AI is used, and where it deliberately isn't

Every arithmetic operation — sums, fees, GST, conservation — is plain, deterministic code, the same way every time. The LLM is used exactly once in the money-adjacent path: forming a hypothesis about the ~4% of cases deterministic matching can't resolve, and even then its output has no authority until independently re-verified from raw data. The gate that decides whether a *verified* correction gets applied automatically is deterministic, has no LLM in it at all, and is tested exhaustively per branch (`gate/policy.py`). `DECISIONS.md` D-07 through D-14 cover this in full, including a real bug (`FAILURES.md` #1) where getting this boundary wrong once — trusting a model's own claimed number for a gate decision — would have mattered more than any other bug in this codebase.
